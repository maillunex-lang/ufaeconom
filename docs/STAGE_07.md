# BUSINESS EMPIRE ONLINE • Этап 0.7: авторитетный сервер экономики

## Что реализовано

- Серверный модуль `server/economy.py` отвечает за все права владельцев, финансы, товары, конкуренцию, производство, маршруты, доставки и рыночные покупки. Данные клиента никогда не принимаются как authoritative balance.
- **Календарь 24/7:** один реальный день равен 30 игровым дням, 48 реальных минут на день, 240 секунд на производственный/торговый субтик, 360 субтиков на месяц. Время задаёт серверный UTC clock. Ночных остановок нет. При рестарте worker догоняет не более 360 тиков за транзакцию, затем продолжает.
- Две тестовые компании `player` и `rival`, NPC-конкурент; администратор может создавать дополнительные компании. Каждая получает стартовые средства из конечного `treasury:central`, а стоимость стартовых предприятий перечисляется поставщикам. **Деньги не создаются при регистрации.**
- Отдельные заводы/магазины/склады, ограниченные запасы и бюджеты, NPC-ценообразование, платные грузовые рейсы с ETA и резервированием складов.
- `server/service.py`: HTTP API 1-го протокола, секреты сессий хранятся только как SHA-256, пароли в базе salted `scrypt`, регистрации через публичный API нет, запросы ограничены по размеру и частоте. Сервис слушает **только loopback**.
- SQLite WAL с единственным process writer lock, транзакционным `world_state` и append-only `finance_ledger`, сохранёнными командами-идемпотентами, online backup и восстановлением после рестарта.
- `scripts/mmo_client.gd` и `scripts/mmo_panel.gd` подключают Android/Godot к серверу через HTTPS: вход, снимки компании, изменение цены и отправка грузов. Клиент не получает права менять деньги/товары/часы. Локальная карта и её сохранения остаются отдельной демонстрацией.

**Это изолированная экономическая MMO beta, а не публичный многошардовый production-сервер.** WebSocket-пуш, внешняя TLS-терминация, настоящие коммерческие аккаунты, мониторинг и отказоустойчивый кластер пока не развёрнуты.

## Запуск для локального тестирования

Требуется Python 3.11+ со стандартной библиотекой; на Lunex проверено на Python 3.14. Рабочий каталог должен быть корнем репозитория. Никакие системные сервисы и Nginx команды ниже не изменяют.

```bash
mkdir -p /tmp/business-empire-beta
python3 -m server.service create-user --db /tmp/business-empire-beta/world.sqlite3 --username demo_player --actor player
python3 -m server.service create-user --db /tmp/business-empire-beta/world.sqlite3 --username demo_rival --actor rival
python3 -m server.service create-user --db /tmp/business-empire-beta/world.sqlite3 --username third_player --actor thirdco --city sterlitamak
python3 -m server.service run --db /tmp/business-empire-beta/world.sqlite3 --host 127.0.0.1 --port 4189
```

Пароль вводится интерактивно через `getpass` (не передавать его в командной строке или GitHub). Для проверки GET `http://127.0.0.1:4189/v1/health`; все финансовые endpoints требуют Bearer-токен. На Android `http://127.0.0.1` указывает на **телефон, не сервер**. Для подключения мобильного приложения нужен собственный HTTPS-домен и закрытый reverse proxy. Не открывайте порт 4189 в интернет.

## Протокол

- POST `/v1/login` c JSON `username`, `password` возвращает краткоживущий session bearer (7 дней).
- GET `/v1/snapshot` возвращает **только собственные** предприятия, деньги и грузы, а также общедоступные торговые предложения.
- GET `/v1/clock` возвращает текущий серверный тик; GET `/v1/ledger?after=<id>` выдаёт финансовые операции своей компании.
- POST `/v1/command` требует `command_id` (уникальный UUID-подобный идентификатор), `expected_revision`, `type`, остальные допустимые поля. Поддерживаются `facility.set_price`, `facility.buy`, `facility.build`, `shipment.create`.
- POST `/v1/logout` отзывает токен. При повторе корректно обработанной команды сервер возвращает прежнюю квитанцию, без повторного списания денег.
- Отсутствуют доверенные клиентские поля `actor`, `tick`, `wallets`, `stock`, `now_unix`.

## Сохранение, резервирование, восстановление

SQLite включает WAL и единственного authoritative writer. При аварии незакоммиченная транзакция не должна изменять `world_state` и ledger по отдельности. Если в сохранённом мире нарушен денежный или товарный инвариант, загрузка останавливается с ошибкой вместо продолжения повреждённой экономики.

Снять согласованную резервную копию **без остановки worker**:

```bash
python3 -m server.service backup --db /tmp/business-empire-beta/world.sqlite3 --output /tmp/business-empire-beta/backup.sqlite3
```

Для ручного восстановления нужно выключить тестовый сервер, сохранить повреждённую БД и её WAL/SHM для диагностики, затем восстановить из проверенной SQLite backup в новый пустой каталог, проверить `PRAGMA integrity_check`, запустить одну копию worker. Не копируйте SQLite только через `cp` при работающем WAL-сервере.

## Android и релизы

APK 0.7.0-beta использует прежнее приложение `com.ufaeconom.business`, отдельную MMO-панель и Android INTERNET permission. Без доступного HTTPS-сервера по-прежнему работает локальная демо-экономика; серверные счета с ней не смешиваются. Сохранения v0.4/v0.5 продолжают читаться локально. Загрузка клиентских сохранений в общую экономику запрещена без отдельной административной проверки.

## Ограничения до публичной беты

- Пока один процесс/одна SQLite БД без шардинга, failover и глобального матчмейкинга. Утверждений о поддерживаемом CCU нет.
- Python HTTP polling каждые 15 секунд, не WebSocket и не real-time движение. Для экономической стратегии подходит для тестов, в будущем потребуется WebSocket delta.
- Python сервер не запускается и не публикуется автоматически. Нельзя считать проект production MMO без инфраструктуры, мониторинга, настоящих нагрузочных тестов и TLS.
- Игровые расстояния и коэффициенты тестовые, баланс на реальных игроках не измерялся. 1000-дневный детерминированный тест проверяет инварианты, а не гарантирует интересность экономики.
- Android на реальном физическом устройстве не проверен. Сборка и подпись APK на Lunex не равны прохождению мобильного smoke-test.
